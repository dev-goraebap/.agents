# 이슈 관리 도우미

개인 또는 소규모 프로젝트의 백로그를 이슈로 운영하기 위한 테일러링된 프로세스.
Use-Case 3.0 의 슬라이스 개념, 스크럼 백로그 운영, 프로토타입 선행 개발
스타일(듀얼 트랙)을 결합했다.

**애자일 전반을 다루지 않는다.** 스프린트 운영, 회고, 추정 포인트, 팀 의식은
범위 밖이다. 이 스킬이 다루는 것은 백로그 항목을 어떻게 쪼개고 이어붙이고
닫느냐 하나다.

**이슈 관리 도구를 만들지 않는다.** GitHub·GitLab 같은 기존 플랫폼을 쓰고,
remote 가 없으면 로컬 마크다운 파일을 쓴다.

1~4절이 공통 규칙이고, 5절에서 상황에 맞는 워크플로우를 골라 들어간다.

## 1. 용어 정의 (공식 어휘)

| 용어 | 의미 | 이슈 구현 |
|---|---|---|
| 하위 도메인 | 문제 영역의 영구 분류 (예: 작업 관리, 알림). 시작/끝이 없다 | 라벨 `domain:*` 또는 Projects 단일선택 필드 |
| Epic | 한시적 이니셔티브. 여러 Feature를 묶으며, 완료되면 닫힌다 | Issue (type: Epic) |
| Feature | 유즈 케이스 1개. "한 사용자가 달성하는 하나의 목표" | Issue (type: Feature). 서술서가 있으면 링크 |
| Story | 슬라이스 1개. 한 이터레이션 안에 완료 가능한 백로그 아이템 | Issue (type: Story), Feature의 sub-issue |
| Task | 기술 작업, 스파이크(프로토타입 포함), 잡무 | Issue (type: Task) |
| 유즈 케이스 서술서 | 지속 갱신되는 요구사항 문서 (선택. 유지한다면 살아있는 산출물) | 레포 docs/ 또는 위키, Feature에서 링크 |

핵심 구분 두 가지:

- **하위 도메인 ≠ Epic.** 초기 구축 때는 "작업 관리 에픽 = 작업 관리 도메인"처럼
  포개져 보이지만 이건 착시다. 하위 도메인은 구조(영구), 에픽은 일 묶음(한시적)이다.
  같은 도메인에 "v2 개편", "성능 개선" 등 에픽이 계속 새로 생기고, "다크 모드"처럼
  여러 도메인을 관통하는 에픽도 있다. 그래서 도메인은 라벨로, 에픽은 이슈로 관리한다.
- **"Feature"는 업계 다의어.** Use-Case 3.0 문서에서 슬라이스의 work item으로
  나열되는 feature는 스토리급 티켓 명칭이고, 이 스킬의 Feature는 SAFe식
  유즈 케이스급이다. 혼동이 감지되면 이 표를 기준으로 정리해준다.

## 2. 공통 규칙

### 계층과 추적성

- 계층: (도메인 라벨) × Epic > Feature > Story > Task
- 계층은 최대 깊이이지 필수 경로가 아니다. Task는 두 용법을 구분한다:
  스토리의 실행 분해(보통 이슈 대신 스토리 본문 체크리스트로 충분)와,
  사용자 가치로 서술되지 않는 작업(스파이크, CI, 리팩토링, 의존성 갱신 등).
  후자는 Story를 거치지 않고 Feature나 Epic 직속으로 붙거나 단독으로 둘 수 있다.
  단, 사용자 가치로 표현 가능한 일은 Task로 도망가지 말고 Story로 쓴다.
- **Task를 항목으로 세울지 체크리스트로 둘지는 "자기만의 완료 조건이 있는가"로
  가른다.** 부모 Story가 닫히면 함께 끝나는 실행 단계는 체크리스트, 독립적으로
  완료를 판정해야 하는 일은 항목이다. 후자에는 스파이크, 기술 검증, 인프라·빌드
  설정, 마이그레이션, 기술 부채 상환이 들어간다. 사용자 가치가 아닌데도 분명히
  끝나야 하는 일이 항목의 자리다.
- 스파이크(프로토타입 등 학습·탐색 목적 작업)는 Task로 등록하며, 범위를
  따라 소속을 정한다: 한 유즈 케이스 범위면 해당 Feature 밑, 여러 Feature에
  걸친 묶음 프로토타입이면 Epic 직속, 기능과 무관한 기술 검증이면 단독.
- Story는 반드시 부모(Epic 또는 Feature)에 연결한다. Feature 층은
  선택적 스캐폴딩이다: 기본은 Epic > Story 2단이며, 스토리 작성 전 "이 사용자의
  목표 전체(유즈 케이스)가 뭔가"를 생각하는 사고는 유지하되 그 결과를 라벨이나
  에픽 본문 목록으로만 남겨도 된다. Feature 항목을 실제로 세우는 것은 유즈 케이스
  하나가 여러 스토리로 쪼개져 묶음 추적이 필요할 때, 서술서를 유지해 링크 걸
  곳이 필요할 때, 또는 사용자가 원할 때다.
- Feature(유즈 케이스) 이름을 짓거나 사용자가 제안한 이름이 수단어(등록·입력·
  조회 등)로 보이면 `references/naming.md`를 읽고 그 원칙대로 판정한다.
- 커밋/PR에 이슈 번호를 남겨 이슈 ↔ 코드 추적이 되게 한다.
- 마일스톤은 시간/릴리스 축(v1.0 등)으로만 쓴다. 이슈당 1개 제한이 있으므로
  스프린트/이터레이션 구분이 필요하면 Projects의 iteration 필드를 쓴다.
- 필터: `type:Epic`, `type:Story`, `parent-issue:`, `no:parent-issue`, `label:domain:*`

### 스토리 템플릿

```
#NN <짧은 기능 요약>
> <역할>로서, <원하는 것>을 하고 싶다. <목적>을 위해.

인수 조건:
- [ ] <조건 1>
- [ ] <조건 2>

type: Story / parent: #<Epic 또는 Feature> / label: domain:<도메인> / milestone: <릴리스>
```

- 항목 1개 = 스토리 1개 = 한 이터레이션에 끝낼 크기. INVEST 점검.
- 인수 조건은 원칙적으로 행동 중심("삭제를 되돌릴 수 있다"). 단, 벤치마킹
  대상이나 디자인이 확정된 경우 구체적 UI 표현("실행 취소 스낵바 5초 표시")을
  허용하고, UI 세부는 디자인 링크로 보완을 우선한다.
- 인수 조건 표기법은 **EARS를 기본 권장**으로 한다. Gherkin(Given-When-Then)을
  쓸지는 상황 판단에 맡긴다:
  - EARS(기본): 규칙·예외·상태 조건을 빠짐없이 서술할 때. 다섯 패턴만 사용 —
    상시("시스템은 항상 ~한다"), When(이벤트), While(상태), If-Then(예외/원치 않는
    동작), Where(선택 기능). 예: "If 제목이 빈 문자열이면, then 시스템은 작업을
    추가하지 않아야 한다."
  - Gherkin: 해당 조건을 자동화 테스트 시나리오로 직결시킬 계획이 명확할 때.
  - 하나의 스토리 안에서 두 표기를 섞지 않는다.
- 삭제 등 작아 보이는 기능도 확인 UX·연쇄 삭제·실행 취소 같은 논의 거리가
  하나라도 있으면 독립 스토리로 뺀다. CRUD 묶음 스토리는 지양.

### 테스트와 완료 기준

- 인수 테스트는 층위가 아니라 임무다. 각 인수 조건은 검증 가능한 가장 싼
  층위에 배분: 로직 → 단위, 비즈니스 규칙 → API/통합, UI 표시·전 구간 관통 → E2E.
- E2E(Playwright 기준)는 핵심 여정만 얇게. 회귀가 무서운 것부터 자동화하고,
  100% 자동화를 목표하지 않는다. 자동화 안 된 조건도 수동 확인 후에 닫는다.
- 프론트/백 분리 시: 백엔드는 API 인수 테스트, 프론트는 목 기반 테스트,
  어긋남 방지는 계약 테스트(Pact 등).
- DoD: 인수 조건 전부 확인 + (서술서를 유지하는 프로젝트라면) 관련 서술서 갱신.

## 3. 듀얼 트랙 개발 흐름

사용자의 스타일: 테일러링된 아키텍처/디자인 시스템 위에서 화면을 목(mock)
데이터로 먼저 만족스럽게 만든 뒤 백엔드를 연결한다. 매핑 규칙:

1. 프로토타입 = 스파이크 Task. 완료 조건은 "화면 확정 + API 계약 초안".
   화면이 마음에 들면 이 항목은 닫힌다.
2. API 계약 우선. 목 데이터는 임의가 아니라 확정된 스펙(OpenAPI)대로 구성(MSW 등).
3. Story는 실동작 시점에 닫는다. 목이 아니라 실제 연결로 인수 조건 충족 시 완료.
4. 묶음 단위 순환. 프로토타입 범위가 제품 전체로 퍼지면 폭포수가 된다.
   Epic(또는 Feature 몇 개) 단위로 프로토타입 → 연결 → 종료 후 다음 묶음으로.

## 4. 어디에 저장하는가

**작업 시작 전에 항상 먼저 판정한다.**

```
git remote 가 있고 GitHub·GitLab 인가?
├─ 예   → 플랫폼 이슈로 발행한다. 이 문서의 표기를 그대로 쓴다.
└─ 아니오 → references/local-backlog.md 를 읽고 로컬 파일로 관리한다.
```

판정이 애매하면(remote 는 있는데 이슈를 안 쓰는 경우 등) 사용자에게 묻는다.

로컬로 시작해도 나중에 플랫폼으로 옮길 수 있다. 계층·라벨·인수 조건 규칙은
양쪽이 동일하고, 담는 그릇만 다르다.

## 5. 워크플로우

| 인자 | 부르는 때 | 읽을 파일 |
|---|---|---|
| `kickoff` | "백로그 세팅해줘", 새 프로젝트 관리 시작 | `references/workflow-kickoff.md` |
| `capture` | "OO 기능 이슈로 만들어줘", 아이디어 언급 (가장 빈번) | `references/workflow-capture.md` |
| `handoff` | "화면 확정됐어", "이제 백엔드 붙이자" | `references/workflow-handoff.md` |
| `tidy` | "백로그 정리해줘", "이 기능 다 된 것 같아", 주기적 점검 | `references/workflow-tidy.md` |

이 스킬이 인자와 함께 호출되면(예: `/plz-help-issues capture 소셜 로그인 추가`)
해당 파일을 읽고 그대로 따른다. 나머지 인자는 그 워크플로우의 입력으로 넘긴다.

인자 없이 호출되었거나 대화 중에 위 트리거가 감지되면, 표에서 맞는 갈래를
스스로 고른다. 어느 쪽인지 판단이 서지 않으면 사용자에게 묻는다.

**한 번에 한 갈래만 읽는다.** 네 워크플로우는 함께 쓰이지 않는다.

## 6. 행동 지침

- 트리거가 감지되면 해당 워크플로우를 따르되, 형식보다 사용자의 흐름을
  우선한다. 의식이 아니라 피드백 루프가 본질이다.
- 용어 혼동(에픽 = 도메인, 피처 다의어 등)이 보이면 1절 표를 근거로 짚어준다.
- 사용자가 규칙과 어긋난 요청을 하면 따르되, 지침과의 차이를 한 줄로 알려준다.
- 이슈 본문, 서술서, README 등 산문을 작성할 때, 문체 규칙을 다루는 스킬이
  설치되어 있으면 함께 적용한다 (과잉 서식·과장어·상투구 제거).
- 백로그 하단은 상세화하지 않는다. 위는 곱게, 아래는 거칠게.
