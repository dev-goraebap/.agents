# 이슈 관리 도우미

개인 또는 소규모 프로젝트의 백로그를 이슈로 운영하기 위한 테일러링된 프로세스.
Use-Case 3.0 의 슬라이스 개념, 스크럼 백로그 운영, 프로토타입 선행 개발
스타일(듀얼 트랙)을 결합했다.

**애자일 전반을 다루지 않는다.** 스프린트 운영, 회고, 추정 포인트, 팀 의식은
범위 밖이다. 이 스킬이 다루는 것은 백로그 항목을 어떻게 쪼개고 이어붙이고
닫느냐 하나다.

**이슈 관리 도구를 만들지 않는다.** GitHub·GitLab 같은 기존 플랫폼을 쓰고,
remote 가 없으면 로컬 마크다운 파일을 쓴다.

1~4절이 공통 규칙이고, 5절에서 상황에 맞는 워크플로우를 골라 들어간다.

## 1. 용어 정의 (공식 어휘)

| 용어 | 의미 | 이슈 구현 |
|---|---|---|
| 하위 도메인 | 문제 영역의 영구 분류 (예: 작업 관리, 알림). 시작/끝이 없다 | 라벨 `domain:*` 또는 Projects 단일선택 필드 |
| **발견 에픽** | **무엇을** 만들지 정하기 위한 묶음. 항목은 스파이크 Task 와 질문 | Issue (type: Epic) + 라벨 `track:discovery` |
| **전달 에픽** | 검증된 것을 **만드는** 묶음. 항목은 Story · Task | Issue (type: Epic) + 라벨 `track:delivery` |
| Story | 슬라이스 1개. 한 이터레이션 안에 완료 가능한 백로그 아이템 | Issue (type: Story), 에픽의 sub-issue |
| Task | 기술 작업, 스파이크(프로토타입 포함), 잡무 | Issue (type: Task) |
| 유즈 케이스 서술서 | **한 사용자가 달성하는 하나의 목표**를 적은 문서. 지속 갱신되는 살아있는 산출물 (선택) | 레포 docs/ 또는 위키. **Story 에서 링크한다** |

### 발견 에픽의 완료 조건

1. 서술서(또는 요구사항)가 확정되었다
2. API 계약 초안이 있다
3. **화면에서 바뀐 동작이 서술서에 반영되어 있다**

셋을 충족하면 닫고, 그 결과로 전달 에픽을 만든다.

### 유즈 케이스는 계층이 아니다

**유즈 케이스는 Story 를 자르기 위한 사고 도구이자, Story 를 묶는 단위다.**
이슈 계층에 자리를 만들지 않는다.

스토리를 쓰기 전에 "이 사용자의 목표 전체가 뭔가"를 그려 보는 것이 핵심이고,
그 결과를 남길지는 그다음 문제다.

| 남기는 곳 | 언제 |
|---|---|
| 아무 데도 (머릿속) | 슬라이스가 두셋이고 금방 끝날 때 |
| **서술서** | 목표와 흐름을 계속 참조할 때. Story 에서 링크한다 |

계층에 칸을 두지 않으므로 **"이 유즈 케이스가 끝났는가"를 판정할 일이 없다.**
목표는 제품이 사는 동안 유효하고, 닫히는 것은 Story 와 에픽뿐이다.

핵심 구분 세 가지:

- **하위 도메인 ≠ Epic.** 초기 구축 때는 "작업 관리 에픽 = 작업 관리 도메인"처럼
  포개져 보이지만 이건 착시다. 하위 도메인은 구조(영구), 에픽은 일 묶음(한시적)이다.
  같은 도메인에 "v2 개편", "성능 개선" 등 에픽이 계속 새로 생기고, "다크 모드"처럼
  여러 도메인을 관통하는 에픽도 있다. 그래서 도메인은 라벨로, 에픽은 이슈로 관리한다.
- **발견 에픽 ≠ 전달 에픽.** 기획이 아직 없는데 전달 에픽이 진행 중이면 트랙을
  잘못 나눈 것이다. 발견의 항목은 스토리가 아니라 **질문과 가정**이고, 발견의
  산출물이 전달의 입력이 된다. 자세한 흐름은 3절.
- **유즈 케이스를 마일스톤으로 쓰지 않는다.** 유즈 케이스는 분류 축이고
  마일스톤은 시간 축이다. 분류가 필요하면 라벨이나 서술서 링크를 쓴다.

## 2. 공통 규칙

### 계층과 추적성

- 계층: (도메인 라벨) × Epic > Story > Task
- 계층은 최대 깊이이지 필수 경로가 아니다. Task는 두 용법을 구분한다:
  스토리의 실행 분해(보통 이슈 대신 스토리 본문 체크리스트로 충분)와,
  사용자 가치로 서술되지 않는 작업(스파이크, CI, 리팩토링, 의존성 갱신 등).
  후자는 Story를 거치지 않고 Epic 직속으로 붙거나 단독으로 둘 수 있다.
  단, 사용자 가치로 표현 가능한 일은 Task로 도망가지 말고 Story로 쓴다.
- **Task를 항목으로 세울지 체크리스트로 둘지는 "자기만의 완료 조건이 있는가"로
  가른다.** 부모 Story가 닫히면 함께 끝나는 실행 단계는 체크리스트, 독립적으로
  완료를 판정해야 하는 일은 항목이다. 후자에는 스파이크, 기술 검증, 인프라·빌드
  설정, 마이그레이션, 기술 부채 상환이 들어간다. 사용자 가치가 아닌데도 분명히
  끝나야 하는 일이 항목의 자리다.
- 스파이크(프로토타입 등 학습·탐색 목적 작업)는 Task로 등록하며, 발견 에픽
  직속으로 붙인다. 기능과 무관한 기술 검증이면 단독으로 둘 수 있다.
- **Story 의 부모는 전달 에픽이다.** 발견 에픽의 자식이 아니다. 전달 에픽이
  아직 없으면 부모를 비워 두고, 전달 에픽이 생길 때 연결한다.
- **Story 는 발견 중에도 미리 써 둘 수 있다.** 다만 **발견이 닫히면 인수 조건을
  다시 본다.** 프로토타입에서 흐름이 바뀌는 일이 흔하므로, 발견 전에 쓴 인수
  조건은 그대로 두면 실제와 어긋난다.
- 유즈 케이스 이름을 짓거나 사용자가 제안한 이름이 수단어(등록·입력·조회 등)로
  보이면 `references/naming.md`를 읽고 그 원칙대로 판정한다.
- 커밋/PR에 이슈 번호를 남겨 이슈 ↔ 코드 추적이 되게 한다.
- 마일스톤은 시간/릴리스 축(v1.0 등)으로만 쓴다. 이슈당 1개 제한이 있으므로
  스프린트/이터레이션 구분이 필요하면 Projects의 iteration 필드를 쓴다.
- 필터: `type:Epic`, `type:Story`, `parent-issue:`, `no:parent-issue`, `label:domain:*`

### 스토리 템플릿

```
#NN <짧은 기능 요약>
> <역할>로서, <원하는 것>을 하고 싶다. <목적>을 위해.

인수 조건:
- [ ] <조건 1>
- [ ] <조건 2>

type: Story / parent: #<전달 에픽> / label: domain:<도메인> / milestone: <릴리스>
서술서: <링크> · 흐름: BF, A2
```

마지막 줄은 **서술서를 유지하는 프로젝트만 쓴다.** 슬라이스는 "어느 흐름을
지나는가"가 정의의 일부라, 그 줄이 없으면 Story → 흐름 추적이 끊긴다.

- 항목 1개 = 스토리 1개 = 한 이터레이션에 끝낼 크기. INVEST 점검.
- 인수 조건은 원칙적으로 행동 중심("삭제를 되돌릴 수 있다"). 단, 벤치마킹
  대상이나 디자인이 확정된 경우 구체적 UI 표현("실행 취소 스낵바 5초 표시")을
  허용하고, UI 세부는 디자인 링크로 보완을 우선한다.
- 인수 조건 표기법은 **EARS를 기본 권장**으로 한다. Gherkin(Given-When-Then)을
  쓸지는 상황 판단에 맡긴다:
  - EARS(기본): 규칙·예외·상태 조건을 빠짐없이 서술할 때. 다섯 패턴만 사용 —
    상시("시스템은 항상 ~한다"), When(이벤트), While(상태), If-Then(예외/원치 않는
    동작), Where(선택 기능). 예: "If 제목이 빈 문자열이면, then 시스템은 작업을
    추가하지 않아야 한다."
  - Gherkin: 해당 조건을 자동화 테스트 시나리오로 직결시킬 계획이 명확할 때.
  - 하나의 스토리 안에서 두 표기를 섞지 않는다.
- 삭제 등 작아 보이는 기능도 확인 UX·연쇄 삭제·실행 취소 같은 논의 거리가
  하나라도 있으면 독립 스토리로 뺀다. CRUD 묶음 스토리는 지양.

### 슬라이스 크기 — 흐름 하나 = 스토리 하나가 아니다

서술서에서 스토리를 뽑을 때 흐름 개수만큼 기계적으로 자르면 스토리가 서너 배로
불어난다. Use-Case 3.0 의 기준을 쓴다.

1. **기본 흐름이 첫 스토리다.** 같은 입력 요소에서 갈라지는 검증·취소 흐름은
   거기에 넣는다.
2. **같은 단계에서 갈라지고 같은 장치로 처리되는 흐름은 한 스토리로 묶는다.**
   원문 예: 결제 정보 오류와 결제 시스템 불능은 둘 다 "결제 문제를 처리한다"
   하나가 된다.
3. **새 입력 요소나 별도 장치(확인 대화, 정렬 등)가 생기면 따로 자른다.**
4. **아직 결정이 안 난 흐름은 자르지 않는다.** 발견이 끝난 뒤에 자른다.

바로 위의 "논의 거리가 있으면 독립 스토리" 규칙과 충돌하지 않는다. 3항이 그것을
포함한다 — 논의 거리가 있다는 것은 대개 별도 장치가 필요하다는 뜻이다.

### 테스트와 완료 기준

- 인수 테스트는 층위가 아니라 임무다. 각 인수 조건은 검증 가능한 가장 싼
  층위에 배분: 로직 → 단위, 비즈니스 규칙 → API/통합, UI 표시·전 구간 관통 → E2E.
- E2E(Playwright 기준)는 핵심 여정만 얇게. 회귀가 무서운 것부터 자동화하고,
  100% 자동화를 목표하지 않는다. 자동화 안 된 조건도 수동 확인 후에 닫는다.
- 프론트/백 분리 시: 백엔드는 API 인수 테스트, 프론트는 목 기반 테스트,
  어긋남 방지는 계약 테스트(Pact 등).
- **경로를 처음부터 끝까지 지나는 테스트(화면·E2E)에만** Story 의 안정된 키
  (슬라이스 ID 또는 Story ID)와 인수 조건 문장을 이름에 붙인다. **단위 테스트에는
  붙이지 않는다.** 함수 하나의 테스트가 인수 조건을 이름으로 가지면 경로가 닫혔다는
  거짓 주장이 된다.
- DoD: 인수 조건 전부 확인 + (서술서를 유지하는 프로젝트라면) 관련 서술서 갱신.

## 3. 듀얼 트랙 — 발견과 전달

**트랙을 둘로 나눈다.** 무엇을 만들지 정하는 일(발견)과 정해진 것을 만드는
일(전달)은 백로그가 다르다. 한 에픽에 섞으면 "기획도 없는데 왜 이 에픽이
진행 중인가"라는 상태가 된다.

| | 발견 트랙 | 전달 트랙 |
|---|---|---|
| 묻는 것 | 무엇을 만들 것인가 | 정해진 것을 어떻게 만드는가 |
| 항목 | 스파이크 Task, 질문 | Story · Task |
| 닫는 조건 | 서술서 확정 + API 계약 초안 + 서술서 갱신 | 인수 조건을 실동작으로 충족 |
| 표시 | 라벨 `track:discovery` | 라벨 `track:delivery` |

로컬 형식에서는 라벨 대신 앞머리에 `track: discovery | delivery` 를 둔다.

### 흐름

**1. 발견 에픽을 연다.**

스파이크 Task 를 만들고 본문에 **"남은 질문"** 절을 둔다. 프로토타입을 만들며
떠오르는 질문과 가정을 여기 적는다.

```markdown
## 남은 질문

- 완료한 할 일을 목록에서 감출 것인가, 회색으로 남길 것인가
- 정렬 기준을 사용자가 고를 수 있어야 하는가
```

답이 나오면 서술서나 Story 메모로 **옮기고 여기서 지운다.** 질문이 두 곳에
남으면 어느 쪽이 최신인지 알 수 없게 된다.

**2. 화면이 확정되면 발견 에픽을 닫는다.**

닫기 전에 두 가지를 한다.

- **서술서를 화면에 맞게 고친다.** 프로토타입에서 흐름이 바뀌는 일이 가장
  잦은데, 이 시점에 반영하지 않으면 서술서가 실제와 어긋난 채 굳는다.
- **API 계약 초안을 확정한다.** 화면에서 역산한다. 목 데이터는 임의가 아니라
  확정된 스펙(OpenAPI)대로 구성한다(MSW 등).

**3. 전달 에픽을 만들고 Story 를 그 아래에 둔다.**

- Story 의 부모는 이 전달 에픽이다
- Story 는 **실동작 시점에** 닫는다. 목이 아니라 실제 연결로 인수 조건을 충족할 때다
- 발견 중에 미리 써 둔 Story 가 있으면 **인수 조건을 다시 본다**

### 묶음 단위로 순환한다

발견 범위가 제품 전체로 퍼지면 폭포수가 된다. Epic 단위로
발견 → 전달 → 종료를 돌고 다음 묶음으로 넘어간다.

## 4. 어디에 저장하는가

**작업 시작 전에 항상 먼저 판정한다.**

```
git remote 가 있고 GitHub·GitLab 인가?
├─ 예   → 플랫폼 이슈로 발행한다. 이 문서의 표기를 그대로 쓴다.
└─ 아니오 → references/local-backlog.md 를 읽고 로컬 파일로 관리한다.
```

판정이 애매하면(remote 는 있는데 이슈를 안 쓰는 경우 등) 사용자에게 묻는다.

로컬로 시작해도 나중에 플랫폼으로 옮길 수 있다. 계층·라벨·인수 조건 규칙은
양쪽이 동일하고, 담는 그릇만 다르다.

## 5. 워크플로우

| 인자 | 부르는 때 | 읽을 파일 |
|---|---|---|
| `kickoff` | "백로그 세팅해줘", 새 프로젝트 관리 시작 | `references/workflow-kickoff.md` |
| `capture` | "OO 기능 이슈로 만들어줘", 아이디어 언급 (가장 빈번) | `references/workflow-capture.md` |
| `handoff` | "화면 확정됐어", "이제 백엔드 붙이자" | `references/workflow-handoff.md` |
| `tidy` | "백로그 정리해줘", "이 기능 다 된 것 같아", 주기적 점검 | `references/workflow-tidy.md` |

이 스킬이 인자와 함께 호출되면(예: `/plz-help-issues capture 소셜 로그인 추가`)
해당 파일을 읽고 그대로 따른다. 나머지 인자는 그 워크플로우의 입력으로 넘긴다.

인자 없이 호출되었거나 대화 중에 위 트리거가 감지되면, 표에서 맞는 갈래를
스스로 고른다. 어느 쪽인지 판단이 서지 않으면 사용자에게 묻는다.

**한 번에 한 갈래만 읽는다.** 네 워크플로우는 함께 쓰이지 않는다.

## 6. 행동 지침

- 트리거가 감지되면 해당 워크플로우를 따르되, 형식보다 사용자의 흐름을
  우선한다. 의식이 아니라 피드백 루프가 본질이다.
- 용어 혼동(에픽 = 도메인, 피처 다의어 등)이 보이면 1절 표를 근거로 짚어준다.
- 사용자가 규칙과 어긋난 요청을 하면 따르되, 지침과의 차이를 한 줄로 알려준다.
- 이슈 본문, 서술서, README 등 산문을 작성할 때, 문체 규칙을 다루는 스킬이
  설치되어 있으면 함께 적용한다 (과잉 서식·과장어·상투구 제거).
- 백로그 하단은 상세화하지 않는다. 위는 곱게, 아래는 거칠게.
