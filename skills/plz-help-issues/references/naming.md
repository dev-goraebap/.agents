# 유즈 케이스 명명 가이드

Feature(유즈 케이스) 이름을 지을 때, 또는 사용자가 제안한 이름이 어색할 때
이 파일을 참조한다. 이름 짓기는 규칙표로 환원되지 않으므로, 원칙과 판정
사례를 함께 둔다.

## 원칙

1. **이름은 액터의 목표다.** 시스템이 하는 일이나 사용자가 거치는 수단이
   아니라, 액터가 달성하려는 상태를 서술한다.
2. **일어나기 테스트.** 사용자가 이 일을 끝내고 자리에서 일어나며
   "됐다, ○○했다"라고 말할 수 있으면 목표 레벨이다. "할 일을 등록했다"로
   일어나는 사람은 없고, "오늘 할 일 정리를 끝냈다"로 일어난다.
3. **수단어를 목표어로 바꾼다.** 등록·입력·저장·조회는 수단이다. 그 수단으로
   무엇을 이루려는지 물어서 이름을 끌어올린다. 목표가 흐름 설계를 끌고 간다:
   "등록"이 목표면 폼 채우고 저장하면 끝이지만, "기록(capture)"이 목표면
   3초 입력, 연속 입력, 잠금 화면 추가 같은 요구가 따라 나온다.
4. **삭제·수정은 독립 유즈 케이스가 아니다.** 상위 목표의 대체 흐름으로 두고,
   슬라이싱할 때 스토리로 뽑는다. 스토리 레벨에서 자연스러운 "삭제"는
   유즈 케이스 레벨에서는 한 목표의 대체 경로다.
5. **목표가 뚜렷이 다르면 유즈 케이스를 분리한다.** 기준은 "액터가 다른
   목표를 갖고 앉았는가"다.

## "관리한다"의 지위

수정·삭제·정리를 아우르는 이름이 필요해서 "관리한다"를 쓰는 것은 타협이
아니다. "내 목록이 현실과 일치하게 유지한다"는 실제 목표가 있기 때문이다.
다만 두 가지를 지킨다.

- 서술서의 목표/가치 필드에 그 목표를 한 문장으로 박아둔다. 이름만 두면
  CRUD 묶음의 이름표로 전락한다.
- "관리한다" 안에 목표가 다른 것이 섞여 있지 않은지 점검한다. 섞여 있으면
  분리한다.

## 흐름 구조와 슬라이싱

목표 하나의 서술서는 대략 이렇게 짜인다.

- 기본 흐름: 최소 성공 경로 (예: 입력 → 확인 → 완료 처리)
- 대체 흐름: 같은 목표의 다른 경로 (예: 내용이 바뀌면 수정, 필요 없으면 삭제)
- 예외 흐름: 원치 않는 상황 (예: 빈 제목 거부)

첫 슬라이스는 기본 흐름만 관통하는 최소 경로, 이후 슬라이스가 대체·예외
흐름을 하나씩 덮는다. 각 슬라이스가 백로그의 스토리가 된다. 유즈 케이스로
묶는 실익이 여기 있다: 스토리만 쌓으면 등록·삭제·수정이 병렬 파편으로
존재하지만, 흐름 점검을 하면 빠진 경로(완료 취소는 어디 갔지?)가 보인다.

## 레벨 구분 (Cockburn)

- 사용자 목표 레벨(해수면): 백로그 뼈대로 삼는 레벨. Feature는 여기에 둔다.
- 하위기능 레벨(수면 아래): "등록한다" 같은 것. 이름 있는 유즈 케이스로
  세우기보다 상위 유즈 케이스의 흐름 속 단계로 둔다.
- 요약 레벨(구름): "업무를 잘 처리한다" 같은 것. 비전 문서용이지 백로그용이
  아니다.

## 판정 사례: 투두 앱 도메인

| 후보 이름 | 판정 | 근거 |
|---|---|---|
| 할 일을 등록한다 | 격하 | 수단어. 상위 유즈 케이스의 기본 흐름으로 둔다 |
| 할 일을 기록한다 (capture) | 채택 | GTD의 capture 개념. "잊기 전에 붙잡아둔다"는 목표가 드러나고, 빠른 입력이라는 품질 요구를 끌고 온다 |
| 할 일을 놓치지 않게 기록해둔다 | 목적은 정확하나 이름이 길다 | 이름은 짧게 두고 목적은 서술서의 목표/가치 필드에 적는다 |
| 할 일을 관리한다 | 조건부 채택 | "목록을 현실과 일치시킨다"로 목표를 명시하면 유효. 명시 없으면 CRUD 이름표 |
| 할 일 목록을 현행화한다 | 채택 | 수정·완료·삭제를 아우르되 목표(목록과 현실의 동기화)가 이름에 드러난다 |
| 오늘 할 일에 집중한다 | 별도 유즈 케이스로 분리 | 액터가 다른 목표를 갖고 앉는다 (MS To Do의 "나의 하루"에 해당) |
| 할 일을 삭제한다 | 유즈 케이스 아님 | "현행화한다"의 대체 흐름. 슬라이싱 시 독립 스토리로는 뽑을 수 있다 |
