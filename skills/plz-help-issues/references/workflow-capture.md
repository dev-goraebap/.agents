# capture — 아이디어를 이슈로

부르는 때: "OO 기능 이슈로 만들어줘", 대화 중 아이디어 언급. **가장 빈번한 갈래다.**

핵심 판단은 두 가지다. **어디에 붙는가**, 그리고 **독립 항목인가 기존 항목에
흡수되는가.**

## 절차

### 1. 소속 확인

이 아이디어가 어느 Feature(유즈 케이스)에 속하는지 찾는다.

| 상황 | 처리 |
|---|---|
| 기존 Feature 에 속함 | 그 밑에 붙인다 |
| 새 유즈 케이스임 | Feature 를 세울지 판단한다 (SKILL.md 2절) |
| 애매함 | **사용자에게 묻는다.** 추측해서 붙이지 않는다 |

기존 백로그를 먼저 조회한다. 로컬이면 `local-backlog.md` 의 조회 명령을 쓴다.

### 2. 독립 항목인가 판단

**기준은 논의 거리의 유무다.**

| | 독립 스토리 | 기존 스토리의 인수 조건 |
|---|---|---|
| 판정 | 확인 UX, 연쇄 효과, 예외 처리 같은 **따로 이야기할 거리가 있다** | 기존 스토리를 설명하면 자연히 따라오는 조건이다 |
| 예 | "삭제를 되돌릴 수 있다" — 실행 취소 UX, 보관 기간, 연쇄 복구가 걸린다 | "삭제 시 확인창을 띄운다" — 삭제 스토리의 조건 하나 |

애매하면 독립 스토리로 뺀다. 나중에 합치는 게 쪼개는 것보다 싸다.

**사용자 가치가 아닌 일이면 Task 로 간다.** 이때 항목으로 세울지 체크리스트로
둘지는 "자기만의 완료 조건이 있는가"로 가른다 (SKILL.md 2절).

### 3. 작성

SKILL.md 2절의 스토리 템플릿을 따른다. 인수 조건은 **행동 중심**으로 도출하고,
EARS 표기를 기본으로 쓴다.

인수 조건을 뽑을 때 확인할 것:

- 정상 흐름만 적지 않았는가 — 예외와 원치 않는 동작을 If-Then 으로 넣는다
- 상태에 따라 달라지는 동작이 있는가 — While 로 넣는다
- 각 조건이 검증 가능한가 — "사용성이 좋다" 같은 것은 조건이 아니다

### 4. 크기 점검

한 이터레이션 안에 끝나지 않을 크기면 **슬라이싱을 제안한다.**

수직으로 쪼갠다. "프론트 먼저, 백엔드 나중"은 수평이라 어느 쪽도 혼자서는
가치를 내지 못한다. "카카오 로그인 먼저, 네이버 나중"처럼 각각이 완결되게 쪼갠다.

### 5. 발행

- 플랫폼: 이슈로 발행하고 부모에 연결한다
- 로컬: 항목 파일을 만들고 `BACKLOG.md` 의 적절한 구획에 링크를 넣는다

발행 위치(어느 구획, 어느 순서)를 사용자에게 확인한다.

## 흔한 실수

| 실수 | 이유 |
|---|---|
| CRUD 를 스토리 하나로 묶는다 | 각각 논의 거리가 다르다. 특히 삭제 |
| 인수 조건에 UI 세부를 적는다 | 디자인이 확정된 경우가 아니면 행동으로 적고 디자인은 링크한다 |
| 사용자 가치를 Task 로 도망친다 | 표현 가능한 일은 Story 로 쓴다 |
| 부모를 안 물어보고 붙인다 | 잘못 붙은 항목은 나중에 고아가 된다 |
| EARS 와 Gherkin 을 섞는다 | 한 스토리 안에서는 한 표기만 쓴다 |
