# kickoff — 프로젝트 착수, 백로그 뼈대

부르는 때: "백로그 세팅해줘", 새 프로젝트 관리 시작.

목표는 **끝까지 채우는 것이 아니라 굴러가기 시작하는 것**이다. 백로그 하단을
상세화하려 들면 착수가 끝나지 않는다.

## 절차

### 1. 저장 위치와 ID 접두어 판정

SKILL.md 4절의 판정을 먼저 한다. 로컬이면 `local-backlog.md` 를 읽고
`backlog/` 위치를 사용자에게 확인한 뒤 디렉터리를 만든다.

**이어서 ID 접두어 충돌을 한 번 묻는다.**

| 계층 | 기본 접두어 |
|---|---|
| Epic | `EP-` |
| Feature | `FT-` |
| Story | `ST-` |
| Task | `TA-` |

이 표를 보여주고 "프로젝트에서 이미 쓰는 ID 체계와 겹치는 것이 있는가"를 묻는다.
도메인 ID 와 충돌하는 경우가 실제로 있다 — 작업(Task) 도메인 제품이 유스케이스
ID 로 `TK-001` 을 쓰는 식이다. 겹치면 비켜 가고, 정한 접두어를 `BACKLOG.md` 맨
위에 적어 둔다.

### 1-1. 마일스톤과 Projects 는 열지 않는다

- **릴리스 계획이 없으면 마일스톤을 만들지 않는다.** 마일스톤은 시간 축이다.
- **Projects 는 이슈가 못 갖는 필드가 실제로 필요할 때만 연다.** 층별(프론트·
  백엔드) 상태처럼. 이슈 목록과 같은 것을 한 번 더 보여줄 뿐이라면 만들지 않는다.
- **유스케이스를 마일스톤으로 쓰지 않는다.** 분류 축과 시간 축을 섞는 것이다.

사용자가 요청하면 만들되, 위 이유를 한 줄로 알린다.

### 2. 비전과 액터 확인

사용자에게 두 가지를 묻는다.

- 제품을 한 줄로 말하면 무엇인가
- 누가 쓰는가 (액터 목록)

**추측해서 채우지 않는다.** 이 둘이 틀리면 아래 전부가 틀어진다.

### 3. 하위 도메인 도출

문제 영역을 영구 분류로 쪼갠다. 시작과 끝이 없는 단위여야 한다.

라벨 체계 `domain:*` 를 제안하고 사용자 확인을 받는다. 이 시점에 도메인이
정확할 필요는 없다. 나중에 라벨을 더하거나 합칠 수 있다.

에픽과 헷갈리면 SKILL.md 1절의 구분을 보여준다.

### 4. Feature 목록 작성

**액터별 목표**를 나열한다. 각 항목이 "한 사용자가 달성하는 하나의 목표"인지
확인한다. 이름이 수단어(등록·입력·조회 등)로 흐르면 `naming.md` 를 읽고 판정한다.

이 단계에서는 목록만 만든다. Feature 항목을 실제로 세울지는 SKILL.md 2절의
기준을 따른다 — 기본은 Epic > Story 2단이다.

### 5. 첫 에픽 — 어느 트랙인지 먼저 정한다

**무엇을 만들지가 정해져 있는가?**

| 상태 | 여는 것 |
|---|---|
| 아직 정하는 중이다 (화면도 요구사항도 미확정) | **발견 에픽.** 항목은 스파이크 Task 와 질문이다 |
| 이미 정해져 있다 (서술서·계약이 있다) | **전달 에픽.** Feature · Story 를 그 아래에 둔다 |

**대부분의 새 프로젝트는 발견부터다.** 기획이 없는데 전달 에픽을 열면 "왜 이
에픽이 진행 중인가"라는 상태가 된다. 확신이 없으면 사용자에게 묻는다.

발견 에픽을 열었다면 여기서 멈춘다. Feature 목록은 4단계에서 만든 것을 에픽
본문에 적어 두고, **Story 로 쪼개지 않는다.** 발견이 끝나야 무엇을 자를지 알 수 있다.

전달 에픽이라면 이어서 슬라이싱한다.

- **최우선 Feature 1~2개만** 스토리로 쪼갠다 (크기 기준은 SKILL.md 2절)
- 나머지는 제목만 남기고 거칠게 둔다

로컬이면 나중 구획은 `BACKLOG.md` 에 한 줄로만 적고 파일을 만들지 않는다.

### 6. 산출물 제시

- 라벨 체계
- Epic / Feature / Story 초안 일괄
- 로컬이면 `BACKLOG.md` 초안까지

발행하기 전에 사용자에게 보여주고 확인을 받는다. 일괄 생성은 되돌리기 번거롭다.

## 흔한 실수

| 실수 | 이유 |
|---|---|
| **기획도 없는데 전달 에픽을 연다** | **발견 에픽이 먼저다. 이 순서가 뒤집히면 에픽 상태가 실제와 어긋난다** |
| 발견 에픽 아래에 Feature 를 단다 | Feature 의 부모는 전달 에픽이다 |
| 모든 Feature 를 스토리로 쪼갠다 | 하단은 곱게 다듬지 않는 게 원칙이다. 요구사항은 바뀐다 |
| 도메인마다 Epic 을 하나씩 만든다 | 도메인은 영구 구조, 에픽은 한시적 묶음이다 |
| 액터를 묻지 않고 시작한다 | 유즈 케이스는 액터의 목표다. 액터가 없으면 Feature 를 세울 수 없다 |
| Feature 층을 항상 세운다 | 선택적 스캐폴딩이다. 묶음 추적이 필요할 때만 세운다 |
| 릴리스도 없는데 마일스톤을 만든다 | 이슈 목록을 한 번 더 보여줄 뿐이다 |
| ID 접두어를 안 묻고 정한다 | 도메인 ID 와 충돌하면 나중에 전부 고쳐야 한다 |
