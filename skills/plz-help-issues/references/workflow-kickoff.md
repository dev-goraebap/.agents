# kickoff — 프로젝트 착수, 백로그 뼈대

부르는 때: "백로그 세팅해줘", 새 프로젝트 관리 시작.

목표는 **끝까지 채우는 것이 아니라 굴러가기 시작하는 것**이다. 백로그 하단을
상세화하려 들면 착수가 끝나지 않는다.

## 절차

### 1. 저장 위치 판정

SKILL.md 4절의 판정을 먼저 한다. 로컬이면 `local-backlog.md` 를 읽고
`backlog/` 위치를 사용자에게 확인한 뒤 디렉터리를 만든다.

### 2. 비전과 액터 확인

사용자에게 두 가지를 묻는다.

- 제품을 한 줄로 말하면 무엇인가
- 누가 쓰는가 (액터 목록)

**추측해서 채우지 않는다.** 이 둘이 틀리면 아래 전부가 틀어진다.

### 3. 하위 도메인 도출

문제 영역을 영구 분류로 쪼갠다. 시작과 끝이 없는 단위여야 한다.

라벨 체계 `domain:*` 를 제안하고 사용자 확인을 받는다. 이 시점에 도메인이
정확할 필요는 없다. 나중에 라벨을 더하거나 합칠 수 있다.

에픽과 헷갈리면 SKILL.md 1절의 구분을 보여준다.

### 4. Feature 목록 작성

**액터별 목표**를 나열한다. 각 항목이 "한 사용자가 달성하는 하나의 목표"인지
확인한다. 이름이 수단어(등록·입력·조회 등)로 흐르면 `naming.md` 를 읽고 판정한다.

이 단계에서는 목록만 만든다. Feature 항목을 실제로 세울지는 SKILL.md 2절의
기준을 따른다 — 기본은 Epic > Story 2단이다.

### 5. 첫 Epic 과 슬라이싱

- 첫 이니셔티브를 Epic 하나로 묶는다
- **최우선 Feature 1~2개만** 스토리로 쪼갠다
- 나머지는 제목만 남기고 거칠게 둔다

로컬이면 나중 구획은 `BACKLOG.md` 에 한 줄로만 적고 파일을 만들지 않는다.

### 6. 산출물 제시

- 라벨 체계
- Epic / Feature / Story 초안 일괄
- 로컬이면 `BACKLOG.md` 초안까지

발행하기 전에 사용자에게 보여주고 확인을 받는다. 일괄 생성은 되돌리기 번거롭다.

## 흔한 실수

| 실수 | 이유 |
|---|---|
| 모든 Feature 를 스토리로 쪼갠다 | 하단은 곱게 다듬지 않는 게 원칙이다. 요구사항은 바뀐다 |
| 도메인마다 Epic 을 하나씩 만든다 | 도메인은 영구 구조, 에픽은 한시적 묶음이다 |
| 액터를 묻지 않고 시작한다 | 유즈 케이스는 액터의 목표다. 액터가 없으면 Feature 를 세울 수 없다 |
| Feature 층을 항상 세운다 | 선택적 스캐폴딩이다. 묶음 추적이 필요할 때만 세운다 |
