# handoff — 발견에서 전달로

부르는 때: "화면 확정됐어", "이제 백엔드 붙이자".

듀얼 트랙의 이음매다. **발견 에픽을 닫고 전달 에픽을 여는 지점**이며, 여기서
서술서와 API 계약이 확정되지 않으면 뒤가 전부 흔들린다.

## 절차

### 1. 발견 에픽의 완료 조건 점검

세 가지를 확인한다.

| 조건 | 확인 |
|---|---|
| 서술서 확정 | 요구사항이 정해졌는가. 흐름이 다 적혔는가 |
| API 계약 초안 | 화면이 필요로 하는 데이터의 모양이 적혀 있는가 |
| **서술서 갱신** | **화면에서 바뀐 동작이 서술서에 반영되어 있는가** |

세 번째가 가장 자주 빠진다. 프로토타입을 만들다 보면 처음 생각과 달라지는 일이
흔한데, 그 변화를 서술서에 옮기지 않으면 실제와 어긋난 채 굳는다.

스파이크 Task 의 **"남은 질문"** 절도 함께 본다. 답이 나온 질문은 서술서나
Story 메모로 옮기고 지운다. **답이 안 난 질문이 남아 있으면 아직 닫을 때가 아니다.**

### 2. 계약이 없으면 먼저 만든다

**계약 미확정 상태로 진행하지 않는다.** OpenAPI 스펙 초안부터 작성한다.

화면에서 역산한다 — 이 화면이 무엇을 보여주고 무엇을 보내는지가 곧 계약이다.
프로토타입의 목 데이터가 임의로 만들어졌다면, 지금 스펙에 맞게 정리한다.

목 구현(MSW 등)은 확정된 스펙대로 다시 맞춘다. 그래야 실 API 교체가 매끄럽다.

### 3. 발견 에픽을 닫는다

완료 조건 셋을 충족했으면 닫는다. 프로토타입 코드를 그대로 쓸지 버릴지는 별개
문제이며, 발견의 완료 판정과 섞지 않는다.

### 4. 전달 에픽을 만든다

발견의 산출물이 전달의 입력이다. 전달 에픽을 열고 라벨 `track:delivery`
(로컬이면 `track: delivery`)를 붙인다.

**Feature 를 여기에 단다.** 발견 중에 Feature 를 미리 만들어 두었고 부모가
비어 있다면, 지금 이 전달 에픽에 연결한다.

### 5. Story 발행 또는 갱신

이 묶음에 해당하는 Story 들을 정리한다. **목 → 실 API 교체 작업을 인수 조건에
포함시킨다.** 프로토타입에서 화면이 돌아간다고 스토리를 닫으면 안 된다.

| 상황 | 처리 |
|---|---|
| 발견 중에 미리 쓴 Story 가 있음 | **인수 조건을 다시 본다.** 확정된 서술서와 대조해 고친다 |
| 스토리가 없음 | `capture` 절차로 새로 만든다. 크기 기준은 SKILL.md 2절 |
| 프로토타입에서 요구가 바뀜 | 인수 조건을 고치고, 바뀐 이유를 메모에 남긴다 |

여기서 스토리를 자를 때 **흐름 하나마다 하나씩 자르지 않는다.** SKILL.md 2절의
슬라이스 크기 기준을 따른다.

### 6. 다음 묶음 확인

사용자에게 묻는다 — **다음 묶음의 발견으로 넘어갈 것인가, 이 묶음의 전달을
끝낼 것인가.**

발견 범위가 제품 전체로 퍼지면 폭포수가 된다. Epic 또는 Feature 몇 개 단위로
발견 → 전달 → 종료의 순환을 유지한다.

## 흔한 실수

| 실수 | 이유 |
|---|---|
| 서술서를 안 고치고 발견을 닫는다 | 화면에서 바뀐 동작이 반영되지 않으면 서술서가 실제와 어긋난 채 굳는다 |
| 답 안 난 질문을 남긴 채 닫는다 | 발견의 목적은 질문을 없애는 것이다 |
| 계약 없이 백엔드부터 짠다 | 화면이 원하는 모양과 어긋나고, 프론트가 다시 기다린다 |
| 발견 중에 쓴 Story 를 그대로 쓴다 | 발견이 닫히면 인수 조건을 다시 본다 |
| 목이 돌아간다고 Story 를 닫는다 | Story 는 실동작 시점에 닫는다 |
| 발견 에픽에 Feature 를 단다 | Feature 의 부모는 전달 에픽이다 |
| 발견을 제품 전체로 확장한다 | 묶음 단위 순환이 무너져 폭포수가 된다 |
