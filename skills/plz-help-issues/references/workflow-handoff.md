# handoff — 프로토타입에서 실구현으로

부르는 때: "화면 확정됐어", "이제 백엔드 붙이자".

듀얼 트랙의 이음매다. **스파이크를 닫고 Story 를 여는 지점**이며, 여기서
API 계약이 확정되지 않으면 뒤가 전부 흔들린다.

## 절차

### 1. 스파이크 완료 조건 점검

해당 스파이크 Task 의 완료 조건은 **"화면 확정 + API 계약 초안"** 두 가지다.

| 항목 | 확인 |
|---|---|
| 화면 확정 | 사용자가 만족했는가. 더 만질 게 남았으면 아직 닫지 않는다 |
| API 계약 초안 | 화면이 필요로 하는 데이터의 모양이 적혀 있는가 |

### 2. 계약이 없으면 먼저 만든다

**계약 미확정 상태로 진행하지 않는다.** OpenAPI 스펙 초안부터 작성한다.

화면에서 역산한다 — 이 화면이 무엇을 보여주고 무엇을 보내는지가 곧 계약이다.
프로토타입의 목 데이터가 임의로 만들어졌다면, 지금 스펙에 맞게 정리한다.

목 구현(MSW 등)은 확정된 스펙대로 다시 맞춘다. 그래야 실 API 교체가 매끄럽다.

### 3. Story 발행 또는 갱신

이 묶음에 해당하는 Story 들을 정리한다. **목 → 실 API 교체 작업을 인수 조건에
포함시킨다.** 프로토타입에서 이미 화면이 돌아간다고 스토리를 닫으면 안 된다.

| 상황 | 처리 |
|---|---|
| 스토리가 이미 있음 | 인수 조건에 실동작 조건을 더한다 |
| 스토리가 없음 | `capture` 절차로 새로 만든다 |
| 프로토타입에서 요구가 바뀜 | 기존 스토리의 인수 조건을 고친다. 바뀐 이유를 메모에 남긴다 |

프로토타입을 만들다 보면 처음 생각과 달라지는 일이 흔하다. **그 변화를
백로그에 반영하지 않으면 스토리가 실제와 어긋난 채 남는다.**

### 4. 스파이크를 닫는다

완료 조건 두 가지를 충족했으면 닫는다. 프로토타입 코드를 그대로 쓸지
버릴지는 별개 문제이며, 스파이크의 완료 판정과 섞지 않는다.

### 5. 다음 묶음 확인

사용자에게 묻는다 — **다음 묶음 프로토타입으로 넘어갈 것인가, 이 묶음의 실구현을
끝낼 것인가.**

프로토타입 범위가 제품 전체로 퍼지면 폭포수가 된다. Epic 또는 Feature 몇 개
단위로 프로토타입 → 연결 → 종료의 순환을 유지한다.

## 흔한 실수

| 실수 | 이유 |
|---|---|
| 계약 없이 백엔드부터 짠다 | 화면이 원하는 모양과 어긋나고, 프론트가 다시 기다린다 |
| 목이 돌아간다고 Story 를 닫는다 | Story 는 실동작 시점에 닫는다 |
| 프로토타입을 제품 전체로 확장한다 | 묶음 단위 순환이 무너져 폭포수가 된다 |
| 프로토타입에서 바뀐 요구를 반영하지 않는다 | 백로그가 실제와 어긋난 채 남는다 |
| 스파이크를 열어둔 채 다음으로 넘어간다 | 완료 조건이 있는 항목이다. 닫고 간다 |
